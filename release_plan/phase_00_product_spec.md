# Phase 00 - Product Spec, Formal Threat Model, Protocol Vision

## Цель

Сформировать научно обоснованный, но инженерно применимый фундамент `Omega` как stealth-first продукта: определить модель противника, режимы продукта, ключевые свойства протокола и измеримые метрики, которые будут реально использоваться в следующих фазах.

## Результат фазы

- Утвержден документ `Omega Protocol v2` как основа всей дальнейшей разработки.
- Утверждена threat model для transport, stealth, relay fabric и control plane.
- Зафиксированы режимы продукта и их trade-offs.
- Определены stealth/performance KPI и правила их расчета.

## Подробное ТЗ

1. **Определить классы противника так, чтобы они реально управляли архитектурой:**
   - пассивный наблюдатель на L3/L4;
   - активный модификатор и инжектор пакетов;
   - активный prober/DPI;
   - провайдер или сеть с нестабильным UDP и принудительной деградацией маршрута;
   - частично компрометированный relay/control контур.
2. **Описать продуктовые режимы как реальные эксплуатационные профили:**
   - `fast`;
   - `balanced`;
   - `stealth`;
   - `hostile-network`.
   Для каждого режима зафиксировать допустимые latency, redundancy, cover-budget, detectability budget и fallback policy.
3. **Определить базовые инварианты протокола:**
   - PFS;
   - сокрытие device identity до безопасной стадии handshake;
   - replay resistance;
   - key update;
   - migration/session continuity;
   - управляемый wire image.
4. **Определить stealth-метрики не как академическое украшение, а как рабочий инструмент:**
   - entropy profile;
   - distribution distance до целевого cover-профиля;
   - probing resistance score;
   - classifier baseline score;
   - cost of stealth в latency/throughput.
5. **Превратить научную часть в проектные решения:**
   - где нужна строгая математика;
   - где достаточно инженерной эвристики с измерениями;
   - какие гипотезы будут проверяться симулятором, а какие сразу кодом.
6. **Зафиксировать, что означает "собственный протокол" в рамках продукта:**
   - свой handshake lifecycle;
   - свой transport frame layer;
   - свой stealth engine;
   - свой relay fabric;
   - свой control plane и policy model.

## Acceptance Criteria

- У команды есть единое понимание целей `Omega v2` и границ системы.
- Каждая следующая фаза опирается на четко зафиксированные инварианты и KPI.
- Для всех ключевых stealth/performance/security метрик определено, как они будут измеряться на практике.
- Открытые исследовательские вопросы не расплывчаты, а сведены к конкретным инженерным решениям или экспериментам.

## Метрики успеха

- Любая новая фича может быть проверена против threat model и продуктовых инвариантов.
- Нет расплывчатых формулировок вида "сделать скрытнее" без численного или экспериментального смысла.
- Первая версия protocol spec уже пригодна для работы команды, а не только для будущего whitepaper.

## Риски

- Излишняя академизация в ущерб скорости реализации.
- Преждевременная фиксация слишком сложных stealth-метрик без данных с реальных стендов.

## Зависимости

- Нет, это фундаментальная база.
